# Эксперимент: помогает ли точное повторение промпта современной LLM

## 1. Цель

Провести воспроизводимую парную A/B-проверку утверждения из препринта *Prompt Repetition Improves Non-Reasoning LLMs*:

- `baseline`: исходный пользовательский запрос отправлен один раз;
- `repeat_2`: тот же запрос целиком вставлен дважды в одно пользовательское сообщение.

Основные исследовательские вопросы:

1. Воспроизводится ли эффект на текущей выбранной модели с отключённым reasoning?
2. Отличается ли эффект на специальных attention-задачах и на обычных пользовательских задачах?
3. Как повторение влияет на входные и выходные токены, стоимость и end-to-end latency?
4. Сколько ошибочных ответов повтор исправляет и сколько правильных ответов ломает?

Источник: https://arxiv.org/abs/2512.14982

В исходной работе основной вариант повторения имел вид `<QUERY><QUERY>`. Авторы сообщили 47 статистически значимых побед из 70 model–benchmark сравнений и ни одного статистически значимого проигрыша при отсутствии пошагового reasoning. Самый вирусный результат — рост Gemini 2.0 Flash-Lite на NameIndex с 21,33% до 97,33%, то есть на 76 процентных пунктов в одной специальной задаче. Это не средний прирост по всем запросам.

## 2. Что именно проверяется

### Первичная гипотеза

На suite `stress` условие `repeat_2` имеет более высокую точность, чем `baseline`.

### Вторичная гипотеза

На suite `practical` эффект меньше, отсутствует либо упирается в потолок высокой baseline-точности.

### Нулевая гипотеза

Для парных заданий вероятность перехода `baseline wrong → repeat correct` равна вероятности перехода `baseline correct → repeat wrong`.

## 3. Неизменяемые правила

1. Использовать прямой API, а не интерфейс ChatGPT, Claude или Gemini.
2. Каждый прогон — новый независимый single-turn request без истории.
3. Инструменты, web search, RAG, memory и file context отключены.
4. Основной прогон выполняется без reasoning:
   - явно отключить его provider-specific параметром; или
   - использовать модель, документированную как non-reasoning;
   - если это невозможно доказать, пометить режим `reasoning_unknown` и не выдавать его за строгую репликацию.
5. Не использовать system prompt. Если API технически добавляет скрытые инструкции, зафиксировать это как ограничение.
6. `temperature = 0`, если параметр поддерживается. Все остальные sampling-параметры одинаковы.
7. В `repeat_2` дублируется **весь user prompt**, включая инструкцию о формате ответа.
8. Между копиями ставится только два перевода строки:

```text
<ORIGINAL_PROMPT>

<ORIGINAL_PROMPT>
```

Нельзя добавлять `Let me repeat that`, «Повторяю», объяснение техники или другие токены: это уже отдельная абляция.

9. Ответы оцениваются кодом по `expected`, без LLM-as-a-judge.
10. Suite `stress` и `practical` анализируются отдельно. Не объединять их в одну headline-accuracy: их веса произвольны.

## 4. Датасет

Файл: `data/tasks.jsonl`

Всего 220 уникальных заданий.

### Stress suite — 160 задач

- `name_index_en`: 40
- `name_index_ru`: 40
- `middle_match_en`: 40
- `middle_match_ru`: 40

`NameIndex`: список из 50 имён, нужно вернуть 25-е.

`MiddleMatch`: список из 40 элементов с повторами; нужно вернуть единственное имя между двумя указанными якорями.

Это адаптация двух специальных задач из статьи. Английская часть ближе к исходной постановке, русская проверяет перенос эффекта на другой язык и токенизацию.

### Practical suite — 60 задач

- `receipt_total_ru`: 12 — стоимость покупки;
- `date_interval_ru`: 12 — дни и полные семидневные интервалы;
- `letter_count_ru`: 12 — подсчёт букв;
- `filter_record_ru`: 12 — выбор единственной записи по нескольким ограничениям;
- `spanish_mcq_ru`: 12 — короткие разговорные переводы в формате multiple choice.

Все задачи имеют однозначный ожидаемый ответ и не требуют внешних данных.

### Пресеты

- `quick`: первые 15 задач каждой stress-категории и первые 4 задачи каждой practical-категории — 80 задач, 160 запросов на модель.
- `standard`: все 220 задач — 440 запросов на модель.

`quick` нужен только для проверки инфраструктуры. Финальные выводы и пост по умолчанию строятся по `standard`.

Перед запуском:

- проверить уникальность `id` и `prompt`;
- проверить обязательные поля;
- посчитать SHA-256 датасета;
- не менять датасет после первого оплачиваемого запроса.

## 5. Условия A/B

### A — baseline

```python
user_content = task["prompt"].rstrip()
```

### B — repeat_2

```python
p = task["prompt"].rstrip()
user_content = p + "\n\n" + p
```

Никакой другой разницы в payload быть не должно.

## 6. Порядок запросов и контроль latency

1. Перемешать task IDs фиксированным seed из конфига.
2. Для каждого task ID отдельно случайно выбрать порядок `AB` или `BA`.
3. Выполнять запросы round-robin, не отправляя сначала все A, а затем все B.
4. Основной режим — `concurrency = 1`, чтобы не смешивать latency с очередью клиента.
5. Перед измерениями выполнить 5 неоцениваемых warm-up запросов на модель.
6. Измерять wall-clock end-to-end latency через monotonic clock.
7. Если API возвращает server timing или time-to-first-token, сохранить отдельно, но не смешивать с end-to-end latency.
8. Если провайдер использует prompt caching, сохранить cached-token fields и показать:
   - номинальные input tokens;
   - billed/cached tokens, если доступны.

## 7. Повторы и вариативность

Стандартный прогон: один ответ на условие для каждого уникального задания.

Перед ним выполнить stability pilot:

- выбрать 20 задач;
- отправить `baseline` дважды с теми же параметрами;
- посчитать долю несовпадающих распарсенных ответов.

Если disagreement > 5%, установить `repeats_per_condition = 3` для основного прогона и анализировать:

- accuracy по всем ответам;
- task-level majority vote;
- вариативность между повторами.

Если disagreement ≤ 5%, одного ответа на условие достаточно, поскольку основной датасет содержит много уникальных пар.

## 8. API и конфигурация

Использовать `config.yaml`. Не хранить ключ в файле или логах: только имя environment variable.

Для каждого model ID сохранить:

- provider;
- точный model ID;
- endpoint/API style;
- дату и время UTC;
- resolved request payload без секрета;
- reasoning mode и способ его отключения;
- temperature, max output tokens, seed и остальные параметры;
- заявленную/фактическую версию модели, если API её возвращает;
- цены на дату прогона и источник цен, если стоимость считается.

Если некоторые параметры API не поддерживает, не имитировать их молча: записать это в `limitations`.

## 9. Retry policy

Повторять только технические ошибки:

- HTTP 408, 429, 5xx;
- network timeout/reset;
- временно пустой или некорректный JSON от API.

Использовать exponential backoff с jitter, максимум 5 попыток.

Нельзя повторять корректный HTTP-ответ только потому, что модель ошиблась или нарушила формат: это часть результата.

Для каждой попытки сохранить status/error. В latency основного ответа использовать длительность успешной попытки; отдельно показать общее время с retries.

## 11. Парсинг и автоматическая оценка

Общая нормализация:

1. Unicode NFKC.
2. `strip()`.
3. Удалить окружающие кавычки и один финальный знак `.`, `,`, `;`, `:`.
4. Для текстовых ответов сравнивать case-insensitive через `casefold()`.
5. Не принимать ответ, в котором после ожидаемого значения есть объяснение, если его нельзя однозначно распарсить.

По `answer_type`:

- `text`: точное нормализованное совпадение;
- `integer`: извлечь единственное целое число и сравнить как `int`;
- `decimal`: принять точку или запятую, сравнить через `Decimal` с двумя знаками;
- `choice`: единственная буква A–D;
- `id`: точное совпадение идентификатора, case-insensitive.

Если в ответе обнаружено несколько возможных значений, ставить `parse_error = true`, `correct = false`. Не угадывать намерение модели.

## 12. Метрики

Для каждой модели, suite и category посчитать:

- `n`;
- baseline correct/accuracy;
- repeat correct/accuracy;
- `delta_pp = 100 × (repeat_accuracy - baseline_accuracy)`;
- `fixed`: baseline wrong, repeat correct;
- `broken`: baseline correct, repeat wrong;
- `both_correct`;
- `both_wrong`;
- exact two-sided McNemar p-value по discordant pairs;
- 95% paired-bootstrap CI для `delta_pp`, минимум 10 000 resamples;
- median, mean, p50, p95 latency;
- median paired latency delta;
- total/mean input tokens;
- total/mean output tokens;
- nominal input-token ratio;
- total и средняя стоимость, если цены доступны.

Проценты в тексте округлять до одного десятичного знака, но в JSON хранить полную точность.

### Exact McNemar

Пусть:

- `b = fixed`
- `c = broken`
- `n = b + c`

При `n > 0` использовать exact two-sided binomial test с `p = 0.5`. При `n = 0`, `p_value = 1`.

Исходная статья обозначала победы при `p < 0.1`. В собственном выводе:

- показывать точный p-value;
- сильное утверждение об эффекте делать при `p < 0.05`;
- при `p ≥ 0.05` писать «статистически ясного эффекта не обнаружено», а не «доказано, что метод не работает».

### Эффект потолка

Если baseline accuracy ≥ 95%, явно указать, что набор близок к потолку и возможный прирост ограничен.

## 13. Интерпретация

Выбрать формулировку отдельно для `stress` и `practical`.

### Улучшение

`delta_pp > 0`, McNemar `p < 0.05`, bootstrap CI не пересекает 0.

### Ухудшение

`delta_pp < 0`, McNemar `p < 0.05`, bootstrap CI не пересекает 0.

### Неясный/нулевой результат

Любой другой случай. Нельзя превращать его в универсальный вывод «повторение не работает».

### Правила честной формулировки

Нельзя писать:

- «Google рекомендует всем повторять промпты»;
- «повтор даёт +76% к точности»;
- «в исследовании не было ни одной ошибки из-за повтора»;
- «мы доказали, что лайфхак умер»;
- «все современные модели…».

Можно писать:

- «три исследователя Google Research выложили препринт»;
- «+76 процентных пунктов в одной специальной комбинации model × task»;
- «ни одного статистически значимого проигрыша среди 70 сравнений»;
- «на протестированной модели и датасете эффект не был статистически ясным».

## 14. Дополнительные абляции — только после primary run

Не смешивать с основной цифрой.

1. `repeat_verbose`: `<QUERY>\n\nПовторяю:\n<QUERY>`
2. `repeat_3`: три точные копии.
3. reasoning on/off для одного и того же model family, если API позволяет.
4. question-first против context-first на отдельном поднаборе.
5. английский против русского.

Абляции запускать только если хватает бюджета. Primary A/B должен быть завершён первым.

## 16. Definition of Done

Эксперимент считается завершённым, только если:

- выполнен standard preset либо явно зафиксирована причина остановки на quick;
- все пары A/B имеют одинаковый task set;
- нет утечки истории между запросами;
- reasoning mode документирован;
- датасет не менялся после начала;
- сырые ответы сохранены;
- все основные ответы оценены автоматически;
- summary пересчитывается из raw data;
- McNemar и bootstrap рассчитаны;
- стоимость и latency не перепутаны с accuracy;
- выводы ограничены протестированной моделью и конфигурацией.
